# sudo-modeling 原則

## 1. 具体から抽象へ (Concrete to Abstract)

**最も重要な原則**: Object Diagramで具体的なインスタンスを作成してから、Domain Modelを抽出する。

```
❌ 悪い例: いきなり「ユーザー」「注文」などの抽象的なクラスを設計
✅ 良い例: 「田中太郎さんがエチオピア産の豆を評価8で記録」という具体例から始める
```

**なぜ重要か**:
- 具体例は曖昧さを排除する
- ステークホルダーとの認識のずれを早期に発見できる
- 必要な属性や制約が自然と見えてくる

## 2. 反復的洗練 (Iterative Refinement)

4つの図（S-U-D-O）を行き来しながら理解を深める。

```
Object → Domain Model → Use Case → System Context
    ↑                                      ↓
    ←───────── フィードバック ←────────────
```

- 各図を作成する度に、他の図に影響がないか確認
- 矛盾が見つかったら前の図に戻って修正
- 完璧を目指さず、段階的に精度を上げる

## 3. ビジネスルール重視 (Business Rules First)

ドメインの制約・ルールを明示的に文書化する。

**含めるべき項目**:
- 値の範囲制約（例: 評価は1-10）
- 必須/任意フィールド
- 状態遷移ルール
- 計算ロジック
- 業務上の制約（例: 自分の評価のみ編集可能）

```typescript
// ルールをコードで表現する例
class Rating {
  // 制約: 1-10の整数のみ
  static create(value: number): Result<Rating, string> {
    if (value < 1 || value > 10) {
      return fail('評価値は1〜10の範囲である必要があります')
    }
    return ok(new Rating(value))
  }
}
```

## 4. 集約設計 (Aggregate Design)

整合性境界を明確に定義する。

**判断基準**:
- 同時に更新される必要があるデータはどれか？
- トランザクション境界はどこか？
- 参照のみで良いデータと、所有すべきデータの区別

```
┌─────────────────────────────────┐
│  CoffeeEvaluation (集約ルート)   │
│  ├── BeanInfo (値オブジェクト)    │
│  ├── ShopInfo (値オブジェクト)    │
│  ├── Ratings (値オブジェクト群)   │
│  └── Visibility (値オブジェクト)  │
└─────────────────────────────────┘
     ↓ 参照（IDのみ）
  UserId (別集約への参照)
```

## 5. 境界づけられたコンテキスト (Bounded Context)

システム境界を意識し、コンテキストマップを作成する。

**考慮すべき点**:
- 同じ用語が異なる意味を持つ場所はないか？
- 外部システムとの連携ポイントはどこか？
- チーム境界とコンテキスト境界は一致しているか？

```
┌──────────────────┐    ┌──────────────────┐
│   評価コンテキスト  │    │  認証コンテキスト  │
│   CoffeeEvaluation│←───│  User            │
│   BeanInfo        │    │  Session         │
└──────────────────┘    └──────────────────┘
        ↓
   userId で参照（ACL経由）
```

---

## 原則の適用順序

1. **Phase 1**: 原則1を適用 - 具体的なオブジェクト例を作成
2. **Phase 2**: 原則3, 4を適用 - ルールと集約を抽出
3. **Phase 3**: 原則5を適用 - コンテキスト境界を確立
4. **全体**: 原則2を適用 - 反復的に洗練
