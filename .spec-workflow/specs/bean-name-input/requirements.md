# Requirements Document

## Introduction

コーヒー愛好家がより詳細な記録を残せるように、コーヒー豆の具体的な名前（商品名や銘柄）を入力・記録できる機能を追加します。現在、「豆の種類」フィールドはありますが、より具体的な商品名や産地、銘柄を記録するための専用フィールドが必要です。この機能により、ユーザーは同じ種類の豆でも異なる銘柄を区別して記録でき、後で特定の豆を見つけやすくなります。

## Alignment with Product Vision

この機能は `product.md` の以下の目標をサポートします:

- **詳細な評価記録**: ユーザーがカフェや豆の詳細な評価を記録したい（Product Purpose）
- **データ品質の向上**: 詳細な評価（全フィールド入力）の割合を高める（Success Metrics）
- **好みのパターン発見**: より詳細な豆の情報により、ユーザーが好みのパターンを発見しやすくなる（User Needs）

現在の実装では「豆の種類」（例: アラビカ、ロブスタ）は記録できますが、具体的な商品名や銘柄（例: エチオピア イルガチェフェ G1、グアテマラ アンティグア）を記録できません。この機能追加により、より精緻なコーヒー体験の記録が可能になります。

## Requirements

### Requirement 1: 豆の名前入力フィールドの追加

**User Story:** コーヒー愛好家として、コーヒー評価を記録する際に豆の具体的な名前（商品名・銘柄）を入力できるようにしたい。そうすることで、同じ種類の豆でも異なる商品や産地を区別して記録できる。

#### Acceptance Criteria

1. WHEN ユーザーがコーヒー評価作成フォームを開いたとき THEN システムは「豆の名前」入力フィールドを表示する
2. WHEN ユーザーが「豆の名前」フィールドにテキストを入力したとき THEN システムは最大255文字まで入力を受け付ける
3. WHEN ユーザーが「豆の名前」フィールドを空欄のまま評価を保存しようとしたとき THEN システムは評価を保存する（任意フィールドのため）
4. WHEN ユーザーが既存の評価を編集するとき THEN システムは「豆の名前」フィールドを表示し、既存の値があれば表示する

### Requirement 2: 豆の名前の表示

**User Story:** コーヒー愛好家として、評価一覧や詳細画面で豆の名前を確認したい。そうすることで、どの豆を評価したかを一目で把握できる。

#### Acceptance Criteria

1. WHEN ユーザーがコーヒー評価一覧ページを閲覧したとき THEN システムは各評価カードに「豆の名前」を表示する（値がある場合）
2. WHEN ユーザーがコーヒー評価詳細ページを閲覧したとき THEN システムは「豆の名前」を明確に表示する
3. IF 「豆の名前」が入力されていない評価の場合 THEN システムは「豆の名前」フィールドを非表示にする、または「未入力」と表示する

### Requirement 3: 検索機能への統合

**User Story:** コーヒー愛好家として、豆の名前で評価を検索したい。そうすることで、特定の豆の過去の評価を素早く見つけることができる。

#### Acceptance Criteria

1. WHEN ユーザーが検索フィールドにテキストを入力したとき THEN システムは「豆の名前」フィールドも検索対象に含める
2. WHEN ユーザーが豆の名前の一部を入力して検索したとき THEN システムは部分一致する評価を表示する（例: 「イルガ」で「イルガチェフェ」がヒット）
3. WHEN 検索結果が表示されたとき THEN システムは一致した「豆の名前」をハイライト表示する（オプション）

### Requirement 4: データベーススキーマの更新

**User Story:** システム管理者として、既存のデータベーステーブルに「豆の名前」カラムを追加したい。そうすることで、既存データを保持しながら新機能を提供できる。

#### Acceptance Criteria

1. WHEN データベースマイグレーションを実行したとき THEN システムは `coffee_evaluations` テーブルに `bean_name` カラム（VARCHAR(255), NULL許可）を追加する
2. WHEN マイグレーション後に既存の評価データを取得したとき THEN システムは既存データを保持し、`bean_name` は NULL として扱う
3. WHEN 新しい評価を作成したとき THEN システムは `bean_name` に入力値を保存する（空欄の場合は NULL）

## Non-Functional Requirements

### Code Architecture and Modularity
- **Single Responsibility Principle**:
  - データベースマイグレーションファイルは `bean_name` カラム追加のみを担当
  - 型定義ファイルは型の定義のみを担当
  - Server Actionsはバリデーションとデータ永続化を担当
- **Modular Design**:
  - フォームコンポーネントは独立して再利用可能
  - 検索機能は既存のロジックに最小限の変更で統合
- **Dependency Management**:
  - 既存のコンポーネント構造を維持（`_components/`, `_containers/`パターン）
  - 既存のServer Actionsを拡張（新しいファイルは作成しない）
- **Clear Interfaces**:
  - TypeScript型定義で `bean_name` フィールドを明確に定義
  - FormData契約を更新して新しいフィールドを含める

### Performance
- **データベースクエリ**:
  - 検索クエリは既存のインデックスを活用（新しいインデックスは不要）
  - `bean_name` への検索追加によるパフォーマンス劣化は最小限（< 50ms）
- **フロントエンド**:
  - フォームレンダリング時間への影響は無視できる程度（< 10ms）
  - バンドルサイズ増加なし（新しい依存関係なし）

### Security
- **入力バリデーション**:
  - XSS攻撃を防ぐため、`bean_name` をサニタイズ（Next.jsのデフォルトエスケープを活用）
  - SQL injection対策（Supabaseのパラメータ化クエリを使用）
- **認証・認可**:
  - 既存のRLS（Row Level Security）ポリシーが `bean_name` にも適用される
  - 自分の評価のみ編集可能（既存の仕組みを維持）

### Reliability
- **データ整合性**:
  - NULL許可のため、既存データへの影響なし
  - マイグレーションのロールバック可能
- **エラーハンドリング**:
  - フィールド長超過時（> 255文字）は明確なエラーメッセージを表示
  - データベースエラー時は既存のエラーハンドリング機構を使用

### Usability
- **UIの一貫性**:
  - 既存のフォームフィールド（店名、豆の種類）と同じスタイルを適用
  - Tailwind CSSの既存パターンを再利用
- **ユーザーガイダンス**:
  - プレースホルダーテキストで入力例を提示（例: 「エチオピア イルガチェフェ G1」）
  - 任意フィールドであることを明示（ラベルに「（任意）」を追加）
- **レスポンシブデザイン**:
  - モバイル〜デスクトップ全てのデバイスで適切に表示（既存の responsive grid を維持）
