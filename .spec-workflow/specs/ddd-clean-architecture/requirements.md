# DDD + クリーンアーキテクチャ導入

## 概要
コーヒー日記アプリにDomain-Driven Design (DDD) とクリーンアーキテクチャを導入し、保守性とテスト容易性を向上させる。

## ユーザーストーリー

### US-1: 開発者として、ドメインロジックを技術的関心事から分離したい
- **理由**: ビジネスロジックの変更が外部技術（Supabase）の変更に影響されないようにするため
- **受入条件**:
  - ドメイン層が外部ライブラリに依存しない
  - 値オブジェクトが自己検証を行う
  - エンティティがドメイン固有の振る舞いを持つ

### US-2: 開発者として、データベース実装を交換可能にしたい
- **理由**: 将来的な技術選定の自由度を確保するため
- **受入条件**:
  - リポジトリパターンによる抽象化
  - 依存性逆転の原則（DIP）の適用
  - DIコンテナによる実装の注入

### US-3: 開発者として、ドメインロジックを単体テストしたい
- **理由**: 高速で信頼性の高いテストを実現するため
- **受入条件**:
  - 値オブジェクトの純粋関数テスト
  - エンティティのドメインロジックテスト
  - モックリポジトリによるユースケーステスト

## 非機能要件

### NF-1: アーキテクチャ制約
- ドメイン層は純粋TypeScriptのみ
- 依存方向: UI → Application → Domain ← Infrastructure
- 各層は明確な責務を持つ

### NF-2: 互換性
- 既存のServer Actionsとの後方互換性維持
- 既存のlib/supabase/からの再エクスポート
